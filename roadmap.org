***** DONE [[https://arxiv.org/abs/0802.3457][Spreadsheet Errors: What We Know. What We Think We Can Do]]
****** What We Know
- Spreadsheets contain errors
  - Across experiments, 51% of spreadsheets contained errors
  - Cell Error Rates were at least 1-2%
- Errors are varied
  - They are like "multiple poisons" - each 100% lethal
  - Quantitatively, they can be mechanical, logical or by omissions
  - Errors can be introduced at any stage of the lifecyle
- Developers are overconfident and Policies Lax - no matter the dev's experience
****** What We Can Think We Can Do
- Cell protection of formula cells to prevent hardwiring errors
- Re-Keying data to prevent data entry errors
- Examining results for "reasonableness" does not work
- Introduce good development practices? - needs to be proven "safe and effective"
- Error Discovery Software - needs to be proven "safe and effective"
- Code Inspection
  - In software, testing comprises 1/3 of development. In spreadsheets, testing is rare
  - Group code inspection is the only experimentally proven way to effectively inspect code
  - This expensive, exhausting and can poor cost-yield tradeoffs (especially in tax auditing)

***** DONE [[https://arxiv.org/abs/0801.0715][Impact of Errors in Operational Spreadsheets]]
Review of real-world spreadsheets in 5 organisations.

Findings:

- Some organizations have spreadsheets that are essentially error-free.
- Within a single organization, spreadsheet practice can range from excellent to
  poor.
- Some organizations use spreadsheets that are rife with errors and some of
  these errors are of substantial magnitude.
- Many errors have zero impact, or impact unimportant calculations.
- There is little correlation between the importance of the application or the
  risk involved and the quality of the spreadsheet.
- Few spreadsheets contain errors that, in the eyes of their developers, would
  destroy their usefulness.

Symptoms of poor spreadsheet practice:

- Chaotic Design
- Embedded numbers
- Special cases
- Non-repeating structures
- Complex-formulas

Reasons cited for poor practice:

- Time pressure
- Organic design
- Changing specs
- Lack of testing
- Lack of relevant knowledge and skills

***** DONE [[https://arxiv.org/abs/0806.3536][In Pursuit of Spreadsheet Excellence]]
Studies the chance of perfect spreadsheets, as observed with organisation 5 in

***** DONE [[https://kilthub.cmu.edu/articles/journal_contribution/Spreadsheet_Errors_and_Decision_Making_Evidence_from_Field_Interviews/6471929/1/files/11901410.pdf][Spreadsheet Errors and Decision Making: Evidence from Field Interviews]]
Interviews spreadsheet users about errors and decision making based on
spreadsheet results. Found that:

- Spreadsheets frequently inform decisions and frequently have errors
- Majority of responders cited instances of this and viewed it seriously
- A non-significant majority found it non-serious.
- Three alternative but not mutually-exclusive explanations were found:
  - Informal quality control methods work reliably for the worst errors.
  - Some spreadsheets are used for various types of information processing, but
    don't inform specific strategic decisions.
  - Even when large errors go undetected, spreadsheets inform but don't drive
    decisions.
- Paper had 3 important results:
  - Field interviews contribute interesting insights, and further research has
    value.
  - Spreadsheets are used for diverse purposes, and not all spreadsheet analysis
    is closely connected to decision making.
  - Research should focus on the final analysis as opposed to the spreadsheets.
**** DONE [2/2] Fraud
***** DONE [[https://arxiv.org/abs/0801.4268][Protecting Spreadsheets Against Fraud]]
Software Development is generally a multi-person effort, while Spreadsheet
Development is typically a single-person process. This makes controlling or
auditing from inside much harder. Also software differentiates between data and
"program", which is not seen in spreadsheets.

Proposes 4 techniques to protect against fraud:

****** Review and Inspection
- Reviews and inspections are the most effective error detection steps
- Line-by-line reviewing can't be effectively translated to spreadsheets
- Separating data and logic significantly improves detection rates and reviewing
  time
****** Testing
- Dijkstra: "testing can only show the presence of faults, but never their
  absence"
- Property-based testing might be more effective
- The integration of data and code makes it that any change to the input data might lead to a change to the program 
- Thus for effective testing for fraud the following are necessary:
  - physical separation of data from code
  - separation of changes to data from changes in code
****** Assertions
- Assertions in essence are property-checks
- Asserting input intermediate, and output "real" (as opposed to test) data
- Deviations point to errors in the model or input data
****** Authentification
- Hash the program portion to prevent unauthorized changes
- Requires strong physical separation of data from code

**** DONE [[https://web.engr.oregonstate.edu/~erwig/papers/SpreadsheetProgramming_ECSE09.pdf][Spreadsheets Programming]]
***** Cells
- A spreadsheet is composed of cells
- Cells addressing can be A1-style, R1C1-style, or named addresses
- Cell references can be relative or absolute 
- Types of cell:
  - Labels - constants not referenced anywhere else
  - Inputs - constants referenced elsewhere
  - Formulas - cells that constitute the spreadsheet program
***** Landscape of Spreadsheet Systems
- VisiCalc first introduced WYSIWYG spreadsheets
- Lotus 1-2-3, Borland Quattro, and MS Excel had the same effect
- Lotus Improv was the first attempt to separate model and data
- Forms/3 pushes the limits of visual programming along with CoreCalc
***** Spreadsheet Research
****** Errors
- Repeats the Panko-Halverson taxonomy
- Quantitative - incorrect results
- Qualitative - poor spreadsheet design and format
****** Design and Maintenance
- "Model Admins" like IT or Database Admins
- Adoption of organisational standards
- Automated spreadsheet audit software
- Spreadsheet education should focus on design and maintenance instead of
  features
- Separate model and data
- ViTSL and Gencel introduce modularity and abstractions
****** Checking, Testing and Debugging
- Consistency checkers like UCheck are useful
- Effective unit testing is difficult, and can give a sense of undue confidence
  if done incorrectly
- Forms/3's What You See Is What You Test methodology makes unit testing easier
- "Help Me Test" can generate test cases
- GoalDebug, a spreadsheet debugger works by defining assertions for a cell
